FluidPD: In-Place Elasticity for SLO-Aware
Prefill-Decode Disaggregated LLM Serving
Kartik Ramesh1, Kaidi Fu1, Zihan Zheng1, Jiahuan Yu1, Fabio Oliveira2, Carlos Costa2, Minjia Zhang1
1University of Illinois Urbana-Champaign
2IBM Research
Abstract—Prefill-decode disaggregation is becoming a common
architecture for LLM serving because it separates two phases
with distinct execution patterns and SLO objectives. Existing
systems typically combine a fixed prefill/decode worker ratio with
request routing across workers. However, real-world workloads
exhibit both short bursts and sustained shifts in the prefill-to-
decode demand ratio. As a result, a configuration that is well
provisioned at one time may quickly become mismatched, causing
latency SLO violations even when idle capacity exists elsewhere.
Existing autoscaling mechanisms can add capacity, but they react
slowly, require spare GPUs, and do not directly address short-
timescale phase imbalance.
We present FluidPD, a P/D-disaggregated serving system
that provides SLO-aware in-place elasticity. FluidPD introduces
two complementary mechanisms. FluidToken handles transient
imbalance by offloading a bounded portion of prefill compu-
tation to decode workers when decode-side slack is available.
FluidRole handles sustained imbalance by reassigning running
workers between prefill and decode roles in place, avoiding
model reload and engine restart. Both mechanisms are guided by
lightweight pressure indices that expose prefill and decode-side
resource pressure before they appear as SLO violations. Across
production Azure trace workloads, FluidPD improves overall
SLO attainment over static SGLang by up to 94.6 percentage
points, demonstrating that SLO-aware in-place P/D elasticity
improves service quality without provisioning additional workers.
I. INTRODUCTION
Large language models (LLMs) are increasingly deployed
in interactive applications, such as chat assistant [32], coding
agent [5], [14], [33], and tool-using workflows [30], [34], [50].
These applications have strict latency demands on both initial
response time and continuous token generation. Prefill-decode
(P/D) disaggregation has become a common architecture for
meeting these demands in LLM serving [35], [54]. By placing
prefill and decode on separate worker pools, it allows each
phase to be provisioned and optimized around its own exe-
cution pattern and Service Level Objectives (SLOs). Prefill
processes the input prompt and largely determines Time-To-
First-Token (TTFT), whereas decode generates output tokens
iteratively and determines Time-Per-Output-Token (TPOT).
This separation makes P/D disaggregation effective for high-
throughput, SLO-aware LLM serving.
However, this separation also makes capacity difficult to
move across phases. In a typical deployment, the numbers
of prefill and decode workers are chosen ahead of time,
often through offline workload profiling [35], [54], and each
worker remains tied to its assigned role at runtime. This
static design has limited flexibility under dynamic workloads.
Production LLM workloads exhibit both short-term bursts and
sustained shifts in request mix [42]. A burst can temporarily
overload prefill workers when many prompts arrive within a
short interval [47], whereas a sustained shift can change the
aggregate prefill-to-decode demand ratio as the workload mix
moves, for example, between prompt-heavy coding requests
and longer interactive conversations [54]. Under a static P/D
partition, routing can balance requests only among workers
already assigned to the required phase [38], [54]. It cannot use
idle decode-side capacity to relieve prefill pressure, nor can it
reassign underutilized prefill capacity when decode demand
grows. Consequently, the system may violate latency SLOs
even when sufficient capacity remains available elsewhere in
the running deployment.
Autoscaling is a natural response to changing demand
and is increasingly supported by production LLM serving
platforms [1], [9], [27]. It is effective when the running deploy-
ment lacks sufficient aggregate capacity, but is less suitable
when capacity is merely distributed poorly between prefill and
decode. Scale-out requires spare GPUs and incurs detection,
provisioning, model loading, and runtime initialization delays.
These delays are too long for short bursts, while scaling
out for sustained phase imbalance adds resources even when
the less-pressured pool already has available capacity. In our
Dynamo [9] experiment, a new worker becomes ready∼200 s
after scale-out is triggered, long after the burst has ended. We
call this missing capability in-place elasticity: adapting the
prefill/decode capacity available within the running deploy-
ment before changing its serving world size.
We present FluidPD, the first P/D-disaggregated serving
system to combine SLO-aware token-level work stealing for
transient pressure with bidirectional in-place role switching
for sustained phase imbalance. FluidPD adapts the prefill
and decode capacity of a fixed set of running workers with-
out changing the serving world size. For short-lived prefill
pressure, FluidToken offloads a bounded suffix of selected
prefill requests to their paired decode workers, allowing
available decode-side capacity to reduce the prefill backlog
without changing worker roles. When phase pressure persists,
FluidRole performs lightweight, bidirectional role switching
between prefill and decode, rebalancing the P/D worker split
within the running deployment without dropping in-flight
requests or provisioning additional workers. Both mechanisms

II. RELATED WORK
A large body of work improves LLM serving efficiency
through advanced batching and scheduling [3], [11], [52], KV-
cache and memory management [13], [20], [23], [53], opti-
mized attention and decoding kernels [4], [10], [31], [37], [46],
[51], CPU offloading [40], [49], model parallelism and pipelin-
ing frameworks [24], [36], and speculative decoding [28], [41].
Other systems use request ordering, admission control, and
batch selection to meet latency SLOs [7], [8], [15], [19], [44].
These techniques improve the efficiency and scheduling of
co-located prefill–decode execution. FluidPD instead targets
P/D-disaggregation, where prefill and decode run on separate
worker pools.
To better accommodate the different compute characteristics
of the prefill and decode phases, recent work has proposed
P/D-disaggregation, which assigns the two phases to separate
GPU workers or worker pools. Systems such as Splitwise [35],
TetriInfer [16], Llumnix [43], and DistServe [54] show that
this separation can improve goodput and TTFT and ITL SLO
attainment while enabling phase-specific execution policies.
Subsequent work introduces additional optimizations for pro-
visioning, scheduling, and KV-cache management [16], [38].
Industry studies further show that the preferred P:D partition
depends on the workload and can change over time [22], [29].

However, these designs primarily optimize a given P/D con-
figuration and do not continuously adapt the running capacity
split as phase demand changes.
Several systems adapt phase capacity by changing worker
roles or serving groups. Arrow [48] routes requests over
stateless instances and reallocates instances between prefill and
decode. DOPD [26] adjusts instance allocation toward a pre-
dicted target P/D ratio, while P/D-Serve [18] supports dynamic
P/D organization at deployment scale. ThunderServe [17] uses
lightweight rescheduling to change phase assignments and
request orchestration in heterogeneous cloud environments. At
a broader deployment level, NVIDIA Dynamo [9], AIBrix [1],
and llm-d [27] provide autoscaling, routing, KV-cache man-
agement, and orchestration for distributed inference. These
systems adapt capacity at worker or serving-group granularity,
but do not exploit token-level work stealing for short-lived
phase pressure.
Other systems share capacity across the P/D boundary
without first reconfiguring whole workers. TaiChi [45] and
WindServe [12] support mixed prefill–decode execution within
an instance, while TokenScale [21] uses pre-provisioned con-
vertible decode workers to absorb prefill bursts. Libra [39],
Kairos [6], and PPD [25] further move request execution
across phase boundaries at token, request, or conversational-
turn granularity. These systems provide either mixed execution
or specialized cross-phase offloading, but do not combine
SLO-bounded token-level work stealing for transient pressure
with in-place worker-role adaptation for sustained changes in
the P/D demand ratio.
III. OBSERVATIONS AND OPPORTUNITIES
P/D-disaggregated serving uses separate prefill and decode
worker pools, but a fixed capacity split may not track changing
workloads. We show that short bursts and sustained demand
shifts both create phase imbalance.
A. Sustained Demand Shifts Break SLOs under Static P/D
Splits
Different LLM applications produce substantially different
prompt and generation characteristics. Prompt-heavy work-
loads generally consume relatively more prefill capacity,
whereas generation-heavy workloads place greater relative
demand on decode. Consequently, changes in the application
mix can shift the effective P/D capacity split required by
the workload over time. Fig. 1 shows the diurnal variation
using one day from the Azure trace [35]. We observe that

A static P/D deployment cannot adapt to this shift because
worker capacity is bound to phase-specific roles. As demand
moves between prefill and decode, a fixed P/D partition can
become poorly matched to the workload even when aggregate
capacity is sufficient. To measure the SLO impact of this
workload shift, we construct Azure (staged), a controlled
workload with three consecutive 10k-request windows that fol-
low an Azure-conversation, Azure-code, Azure-conversation
sequence; its construction is described in detail in § V-A. We
evaluate the workload using Llama-3.1-8B at a constant 40
RPS Poisson arrival rate on an 8×A100-80GB server and
compare 4P4D, 5P3D, and 6P2D deployments, using TTFT
and TPOT SLOs of 2000ms and 100ms. We define the oracle
P:D ratio for each window as the static ratio with the highest
overall SLO attainment. Fig. 2 shows that no single static
partition performs well across both workload types: 4P4D
reaches 86.93% SLO attainment on Azure-conversation but
only 3.40% on Azure-code. In contrast, 6P2D reaches 99.40%
on Azure-code but only 6.64% on Azure-conversation. The
oracle performs well by selecting a different P/D split for
each window, which shows that the SLO loss comes from
P/D imbalance rather than insufficient total capacity.
B. Short Bursts Create Transient P/D Imbalance
Workload variation also occurs at a much shorter timescale.
We define a burst as a brief interval in which arrival or token
demand rises sharply. Unlike the sustained shifts in § III-A,
a burst does not necessarily change the long-term workload
mix. To measure the effect of such bursts, we construct Azure
(mixed), a 10K-request workload composed of Azure-code and
Azure-conversation requests; its construction is described in
detail in § V-A. We replay it using Llama-3.1-8B on 8×A100-
80GB under a static 4P4D deployment, with TTFT and TPOT
SLOs of 2000 ms and 100 ms, respectively. Fig. 3 shows the
resulting burst-induced prefill pressure. During the marked
burst, input-token demand rises from a median of 98.0K to
109.3K tokens/s. The burst rapidly builds a prefill waiting
queue, causing TTFT to exceed its SLO. More importantly,
the impact of this burst lasts longer than the burst itself. New
requests arriving during and after the burst must wait behind

that temporarily exploits decode-side slack without changing
worker roles.
C. Autoscaling Is Often Coarse for P/D Imbalance
Autoscaling is a common approach to handling changes in
inference demand. Systems such as Dynamo, AIBrix, and llm-
d can add or remove inference workers as load changes [1],
[9], [27]. This capability is important when total workload
demand changes over long timescales, but it is less suitable
for the two forms of phase imbalance identified above.
For short bursts, autoscaling incurs both detection and
actuation delay. The controller must first observe a lagging
symptom, such as latency degradation or high resource uti-
lization. By the time the scale-out condition is detected, the
burst may already have produced a substantial backlog. After
the decision, the newly allocated capacity must be provisioned
before it can serve requests.
To quantify these delays, we deploy Llama-3.1-8B with
Dynamo’s SGLang backend and disaggregated planner on
the same Azure (mixed) workload. Starting from a 3P3D
deployment under an 8-GPU budget, Dynamo issues a scale-
out decision roughly 5 s after the burst begins. However,
the added worker becomes ready only about 200 s later:
approximately 100 s elapses before Kubernetes creates the pod,
including scheduling and resource provisioning, and a further

running deployment. Autoscaling is therefore well suited to
aggregate-capacity shortages, but can be too slow for short
bursts and too coarse when capacity is imbalanced across
prefill and decode.
IV. SYSTEM DESIGN
FluidPD provides in-place elasticity for P/D-disaggregated
LLM serving. Its goal is to adapt the effective prefill/decode
capacity available to a running deployment without immedi-
ately changing the serving world size.
A. Overview
Fig. 5 shows the architecture of FluidPD. FluidPD builds on
the standard P/D-disaggregated structure with separate prefill
and decode worker pools and a router that assigns each re-
quest to a prefill/decode worker pair. FluidPD then introduces
two elasticity mechanisms. FluidToken provides request-level
adaptation. When a prefill worker estimates that its queued
requests are at risk of violating TTFT, it can ask the paired
decode worker to execute a suffix of selected prefill requests.
This token-level work stealing reduces prefill queuing delay
without changing worker roles. Since the stolen work runs on
a decode worker, FluidToken allows stealing only when the
decode worker has sufficient slack and memory headroom,
preventing TTFT gains from causing TPOT violations or
decode-side backpressure.
FluidRole provides worker-level adaptation. When phase
pressure persists, FluidPD changes the effective P/D ratio by
switching selected workers between prefill and decode roles
in place. Unlike auto-scaling, FluidRole keeps model weights
and runtime state, and changes the active role of an existing

B. FluidToken: Pressure-Guided SLO-Aware Token Stealing
1) Token-Stealing Execution: FluidToken steals work from
prefill to decode, targeting the short-term bursts in § III-B,
where prefill queues build while decode-side slack remains
available. It implements this stealing as a partial-prefill handoff
along the request’s existing P/D execution flow, as shown in
Fig. 6. For a request iwith prefill length Li, FluidToken selects
a stealing ratio βi ∈[0,1] using the policy in § IV-B3, yielding
a prefill-side prefix of length Lpfx = (1−βi)Li and a decode-
side suffix of length Lsfx = βiLi.
After the prefill worker computes the prefix and transfers its
KV states, the decode worker executes the suffix by treating
the transferred KV as prior context, as in chunked prefill [3].
Each suffix token therefore observes the same causal mask and
position ordering as it would in an unsplit prefill, making split
execution mathematically equivalent to unsplit. After prefilling
the suffix, the decode worker generates the first token and
inserts the request into the decode batch.
As shown in Fig. 6, FluidToken reuses SGLang’s async
P/D KV-transfer path [53]. During the prefix-KV transfer,
both workers continue processing other requests, overlapping
the handoff with concurrent prefill and decode execution.
FluidToken therefore redistributes rather than reduces prompt
computation. Its benefit comes from moving part of the
queued prefill work to a decode worker with available slack,
allowing the prefill worker to begin subsequent requests earlier.
Fig. 7 illustrates this effect. FluidToken splits request R2, and
schedules just the prefix R2pfx on the prefill worker. This
allows request R3 to start prefill earlier and meet its TTFT
SLO.

Executing a stolen suffix introduces two decode-side costs.
First, the suffix forward pass temporarily defers the next de-
code iteration. Second, earlier admission of the stolen request
increases decode-side KV occupancy and may reduce the
worker’s headroom for subsequent requests.
To address this, FluidToken admits stolen work only when
the paired decode worker has sufficient TPOT slack and KV-
cache headroom. The pressure signals and policy that enforce
these conditions and determine the maximum admissible suffix
length are described next.
2) Prefill-Decode Pressure Signals: FluidToken uses two
phase-specific signals. The Prefill Pressure Index (PPI) pre-
dicts whether queued requests are at risk of missing their
TTFT SLOs and therefore whether token stealing is needed.
The Decode Pressure Index (DPI) captures whether the paired
decode worker has sufficient resource and admission headroom
to accept stolen work.
Directly using observed TTFT and TPOT alone is insuffi-
cient for this decision. They are lagging indicators, and the
same latency symptom can arise from different bottlenecks.
In particular, elevated TTFT may result either from prefill
overload or from decode-side admission backpressure. In
P/D-disaggregated serving such as SGLang [53], the decode
worker reserves KV-cache capacity before prefill execution
begins. Insufficient decode-side KV-cache headroom can block
a request from entering prefill, even when prefill compute
remains available. FluidToken therefore uses PPI and DPI to
distinguish prefill deadline pressure from decode-side pressure
before an SLO violation occurs.

C. FluidRole: In-Place Role Switching
FluidToken handles transient prefill pressure without chang-
ing worker roles. When phase imbalance persists, FluidRole
changes the effective P/D worker ratio by switching an existing
worker between prefill and decode roles in place.
1) Role-State Expansion and Bidirectional Live-Role Mi-
gration: FluidRole extends the runtime with a role-switching
state machine (Fig. 8) comprised of three states: ACTIVE,
DRAIN, and SWITCH. In ACTIVE, the worker executes the
scheduler and KV-transfer path of its current role. Upon
receiving a switch request, the worker transitions through
three states: ACTIVE(old role) →DRAIN →SWITCH →AC-
TIVE(new role). It first enters DRAIN, where it stops accepting
new work and waits for in-flight operations to reach a safe
boundary. It then enters SWITCH, where FluidRole activates
the target role’s queues, transfer handlers, and scheduler state.
FluidRole changes a worker’s serving role while preserving
its model placement and parallelism configuration. The worker
therefore reuses its existing model-parallel communication
groups throughout the transition. When switching into the
decode role, FluidRole initializes the required decode CUDA
graphs within the existing worker process, without restarting
the engine or reloading model weights. In the current imple-
mentation, these graphs are captured on the first switch into
decode and remain cached for subsequent switches, so only
the first transition incurs the capture overhead. Capturing the
graphs for both roles at startup would eliminate this first-
switch cost, at the expense of additional GPU memory for
retaining both sets of CUDA graph state. The worker finally
returns to ACTIVE and resumes serving under the new role.

FluidRole switches roles without dropping requests or caus-
ing downtime, even when the selected worker is serving
requests under its current role. Unlike restart-based reconfigu-
ration, role switching avoids the downtime caused by process
startup, model loading, and distributed initialization, but still
requires the worker to drain role-specific in-flight work before
the transition can complete. The key idea is to reassign work
that has not yet started while draining work that is already in
progress. Queued requests can be removed from the worker
and reassigned to another worker with the same current role.
In-progress requests remain on the selected worker until they
reach a safe transition boundary. Because the amount and
duration of in-progress work differ between prefill and decode,
the resulting drain cost is directional.
For a P→D switch, the worker stops admitting new pre-
fill requests, reassigns queued requests that have not started
execution, completes its current prefill batch, and flushes
any outstanding KV transfers. Its drain time is therefore
bounded primarily by the remaining prefill execution and
non-overlapped KV-transfer time. For a D→P switch, the
worker stops admitting new decode requests and allows its
active requests to finish before activating the prefill role.
These requests already hold local KV state and may continue
generating until EOS or the configured maximum generation
length. Because their remaining output lengths are unknown at
switch time, the drain time depends on the longest remaining
active sequence and can be substantially larger than for a P→D
switch. We quantify these overheads in § V-H.

switch recommendation persists for Npersist consecutive in-
tervals. This prevents short-lived pressure fluctuations from
triggering role changes. Once this happens, FluidRole selects
the worker with the smallest estimated drain cost. For D→P
transitions, where the remaining output lengths are unknown,
FluidRole uses the number of active decode requests as a
lightweight proxy for drain time. The controller switches one
worker at a time and favors the candidate expected to reach
the safe switching boundary with the least disruption. After a
switch, the controller enforces a cooldown period Tcooldown
before considering another transition, allowing the new P/D
configuration to take effect. Together, Npersist and Tcooldown
prevent rapid or repeated role changes when workload demand
fluctuates near the decision thresholds.
V. EVALUATION
A. Evaluation Methodology
Implementation: We implement FluidPD on top of SGLang
[53], a production-grade LLM serving engine with P/D disag-
gregation support. FluidPD extends SGLang’s disaggregated
runtime (v0.5.4) with FluidToken and FluidRole while pre-
serving SGLang’s standard P/D execution flow, including
prefill-side scheduling, decode-side KV-cache preallocation,
asynchronous KV transfer, and CUDA Graph execution. A
deployment with N prefill workers and M decode workers
is denoted as NPMD. Our current predictor implementation
relies on offline profiling. Online recalibration from observed
8

===== PDF PAGE 9 =====
execution times is a natural extension for tracking runtime
variation and workload drift.
Models and workloads: We evaluate FluidPD on three LLMs
with different serving characteristics: Llama-3.1-8B, Qwen3-
14B, and Qwen3-30B-A3B (MoE). We evaluate FluidPD using
workloads derived from the Azure LLM Inference trace [42],
which provides separate Azure-code and Azure-conversation
traces spanning one week each. These traces contain substan-
tial variation in request mix, arrival rate, and short-timescale
arrival burstiness. Because replaying the complete 168-hour
trace for every configuration is prohibitively expensive, we
construct two representative workloads. Azure (staged) con-
tains 30K requests arranged as three 10K-request stages:
Azure-conversation, Azure-code, and Azure-conversation.
Azure-code is more prefill-heavy because its requests tend
to have longer prompts and shorter generations, whereas
Azure-conversation places relatively more pressure on decode
through longer output streams. The staged workload therefore
captures sustained shifts in the preferred P:D ratio. Azure
(mixed) contains 10K naturally interleaved requests from a
bursty trace window, capturing the short-timescale variation
described in § III-B. We replay both workloads at controlled
request rates.
Baselines and configurations: We compare FluidPD against
SGLang v0.5.4, vLLM v0.26.0, and Dynamo v1.3.0. The
SGLang and vLLM baselines use static 4P4D deployments,
while FluidPD starts from the same 4P4D allocation and
adapts its effective P:D capacity in place. We evaluate Dynamo
both as a static 4P4D deployment under the same 8-GPU
budget and, in a separate autoscaling comparison, as a 6-GPU
deployment that can grow to 8 GPUs. All evaluated config-
urations use round-robin request routing. We do not directly
compare with TaiChi, TokenScale, or Libra [39] (DynaServe in
its preprint version) because no public implementations were
available at the time of evaluation.
Metrics: We use overall SLO attainment as the primary
metric, following [35], [48], [54]. TTFT and TPOT SLOs
define upper bounds for the corresponding latency metrics,
and attainment rate is the percentage of requests satisfying
each bound. Overall SLO attainment is the percentage of
requests that satisfy both bounds. In the main results, TPOT
SLO is 100 ms for all models, while TTFT SLO is 1000 ms
for Qwen3-30B-A3B, 2000 ms for Llama-3.1-8B, and 3000 ms
for Qwen3-14B.
Hardware testbed: All experiments run on an AWS server
with 8× NVIDIA A100-80GB GPUs interconnected via
NVLink, using one GPU per serving instance.
B. Main Results
Fig. 9a evaluates whether in-place P/D elasticity improves
SLO attainment over static 8-GPU deployments as the offered
request rate increases. Across both Azure workloads, FluidPD
improves overall SLO attainment under pressure. Compared
with static SGLang, FluidPD improves overall SLO attainment
by up to 94.6 percentage points on Azure (staged) and by
up to 74.3 percentage points on Azure (mixed). The largest
gains appear at low and moderate offered loads, where the
fixed baselines become mismatched to workload phase demand
even though the deployment still has usable aggregate capacity.
FluidPD can exploit this headroom by reassigning workers for
sustained shifts and temporarily borrowing decode-side slack
for shorter bursts. At higher offered loads, the deployment
approaches saturation, leaving less spare capacity for either
mechanism.
Fig. 9b breaks down this effect for Llama-3.1-8B on Azure
(mixed). In SGLang’s P/D-disaggregated execution, both sus-
tained phase shifts and transient bursts first create admission-
side pressure at the prefill workers, increasing TTFT violation.
As a result, FluidPD’s overall SLO improvement primarily
comes from higher TTFT attainment, while TPOT attainment
remains close to the baselines through most of the sweep. At
the highest offered load, FluidPD’s TPOT attainment decreases
slightly. This happens because partial-prefill execution on
decode workers consumes decode-side slack; once the system
is saturated, stolen prefill work can interfere with decode
iterations enough to create TPOT violations.
We next compare FluidPD with autoscaling to determine
whether adding workers can address the same P/D imbalance
that FluidPD resolves within the running deployment. We
run Llama-3.1-8B on Azure (mixed) and Azure (staged).
Both systems start from the same 6-GPU 3P3D configuration.
FluidPD remains within these six GPUs, whereas Dynamo
may scale the deployment to eight GPUs. Fig. 9c shows
that autoscaling reacts slowly to the imbalance timescales in
both workloads. On Azure (mixed), the dominant event is a
short prefill-heavy burst. At 20 RPS, FluidPD achieves 97.6%
overall SLO attainment, compared with 9.3% for Dynamo.
Dynamo initiates scale-out after the burst begins, but the new
worker becomes available only hundreds of seconds later, after
the burst has already caused substantial TTFT violations. In
contrast, FluidPD responds within the existing deployment:
FluidToken borrows available decode-side slack to execute
bounded prefill work and reduce queueing without waiting for
additional workers. Azure (staged) contains a longer-lasting
demand shift and is therefore more favorable to autoscaling.
Nevertheless, at 20 RPS, FluidPD achieves 92.6% overall SLO
attainment, whereas Dynamo achieves 5.2%. Under Dynamo’s
active planner, the deployment repeatedly changes its P/D
allocation, including removing workers and later adding them
back, and does not converge quickly to a configuration that
matches the workload. FluidPD instead adjusts the P/D split
among already-running workers through FluidRole and uses
FluidToken to absorb shorter pressure intervals.

D. Component Ablation
To isolate the contribution of each mechanism, we com-

F. Hyperparameter Sensitivity
FluidPD exposes several control parameters that determine
how aggressively it reuses capacity across phases. For Flu-
idToken, one important parameter is the budget factor η,
which scales the TPOT-derived suffix-execution bound. A
larger ηrelaxes this bound, allowing the solver to admit larger
stolen suffixes to reduce prefill queueing but introduces decode
interference. In our runs, we find η = 1.25 to balance this
trade-off. For FluidRole, the key parameters are the PPI and
DPI thresholds that control when the controller changes the
P:D allocation. These thresholds are important because they
directly control reaction time: overly conservative values delay
adaptation, while overly aggressive values can cause churn.
We find PPI-low = 0.6, PPI-high = 1.0, DPI-load = 0.6, and
DPI-admission = 0.2 to be a good combination.
G. Predictor Model Accuracy
FluidPD uses lightweight latency predictors to estimate
prefill execution, stolen-suffix execution, and decode-iteration
latency. We calibrate these predictors offline for each model
and hardware configuration evaluated in this work. The con-
troller does not require a universally valid analytical model. It
only requires sufficiently accurate estimates over the operating
range of the deployed configuration. Fig. 13 compares pre-
dicted and measured execution times over the profiled range.
The predictions closely track the measurements, with relative
error within 2–10% for most profiled points. This accuracy
is sufficient for online control because FluidPD uses the
predictions to enforce conservative stealing and role-switching
constraints, rather than to estimate exact end-to-end request
latency.

VI. CONCLUSION
In this work, we present FluidPD, a P/D-disaggregated LLM
serving system that adapts capacity in place under both tran-
sient bursts and sustained shifts in phase demand. FluidToken
uses SLO-aware token-level work stealing to exploit decode-
side slack, while FluidRole rebalances the running P/D worker
split through in-place role switching. Guided by predictive
pressure signals, FluidPD improves overall SLO attainment
by up to 94.6 percentage points on Azure trace workloads
while largely preserving TPOT attainment outside overloaded
ranges. These results show that P/D imbalance can often be
addressed using capacity already present in the deployment,
before resorting to additional GPUs.
