2 Background
MLA and its KV cache. MLA [1] projects each token’s
keysandvaluesintoonelow-ranklatentvectorsharedbyall
attention heads. The per-token KV state is therefore small
and independent of the head count. For GLM-5.3 in FP8, one
256-token LMCache chunk covering all layers is 12.4MB, so
𝑠≈48.4 KBpertoken. SplittingattentionheadsacrossGPUs
(tensorparallelism)doesnotshrinkthisstate,becauseevery
head needsthefulllatent.
Prefill context parallelism. PCP [13, 17, 25] splits the
prompt along the sequence, so each of the𝑊 ranks processes
about 1/𝑊 of the tokens. Ranks exchange KV with an All-
Gathersothatcausalattentionseeseveryearliertoken;after
theexchangeeveryrankholdsthewholeprompt’slatentKV.
In our deployment the MoE layers additionally use expert
parallelism (EP8). Every forward step contains NCCL collec-
tives, so the ranks run in lockstep: anything that delays one
rank delays all of them.
Prefill/decode disaggregation. Prefill is compute-bound
and decode is memory-bandwidth-bound, so separating them
lets each use its own parallelism and batchlimits [21, 27]. A
routersends eachrequestto aprefill engine, which computes
(or loads) the prompt’s KV and ships it to a decode engine
over NIXL[20]; the decode engine streamstheanswer.
LMCache. LMCache [19] splits KV into fixed-size chunks
keyedbyahashofthetokenprefix,soachunk’skeyidentifies
everything before it. A lookup returns the longest prompt
prefixwhosechunksareallpresent;agapmeanseverything
afteritisrecomputed. ForMLA,LMCachestoresandloads
only on worker 0 (save_only_first_rank), since every
tensor-parallel rank holds the same latent KV. The remote
backend speaks the RESP protocol to a Redis-compatible
server,throughanativeclientthatkeepsapoolofconnections
per engineworker.
Valkey. Valkey [24], like Redis, executes every command
on a single main thread; I/O threads only parallelize socket
reads and writes. A singleinstance’s command throughput is
thereforebounded byone core, whatever theclient count.

Shrink the fixed cost. Our 𝑇0 ≈0.33 s means that, on

Staticpartitionsmakescale-outfree. Therankpartitioning

Lockstepamplifieseverything. UnderPCP,anyper-rank

8 Limitations
• Singleruns. Eachconditionwasrunonce. Thelargeeffects
(124×atp99,6.3×bandwidth,theunstablequeue)arefar
outside run-to-run variation, but differences under about
10% (for example H3 againstH4)are notestablished.
• Prefillonly,oneengine. Thereplaysomit the KVhandoff
to decode and use one engine as the only Valkey client;
contention from several engines on shared instances is
estimated,notmeasured. Attheworkload’s∼0.45requests/s
perengineand0.79GBperprompt,sixengineswoulddraw

• One prompt-length bucket. Latency results are for 14.7k–

Loadversusrecompute. CacheGen[18]compressesKVto

10 Conclusion
A remote KV tier is only useful if it beats recomputation, and
oncurrentGPUsthatisahighbar: forGLM-5.3onaB300
node, a cache hit must arrive at more than 2.53GB/s, and a
fixedenginecostputsshortpromptsoutofreachaltogether. A
singlekey-valueservercouldnotmeetthebar,andsynchronous
loading turned the shortfall into an unstable queue. Sharding
theMLAKVstoreacrosscontext-parallelranksspreadscache
I/Oevenly,anditsstaticownershipletstheremotetierscale
outbyrankwithnocoordination. Togetherwithasynchronous
loading and three client fixes, thisbrings hit-heavy p99from
83.32s to 0.67s.
