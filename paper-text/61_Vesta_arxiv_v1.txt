Abstract
Agentic applications generate multi-turn sequences of LLM
requests, with each new turn extending the context accumu-
lated from prior interactions and tool calls. Prefix caching
reuses the KV cache of earlier turns and avoids redundant
prefill, but routing every turn to its cache-affine instance
can create severe local queues while capacity remains idle
elsewhere. Remote KV cache access relaxes this tension, yet
migrating execution adds transfer work and is harmful when
the cluster is already congested. Thus, deciding where to exe-
cute a request requires reasoning jointly about cache locality,
queueing, and the current operating point of the cluster.
We present Vesta, a queueing-aware scheduler for dis-
tributed agentic LLM serving. Vesta assigns each session a
stable holder for its authoritative KV cache while indepen-
dently selecting an executor for every request. Grounded in
classical queueing theory, its objective accounts for backlog,
reusable prefixes, KV cache transfer, and the queueing exter-
nality of additional service demand; it migrates execution to
recover idle capacity when beneficial and favors placements
that add the least prefill and transfer work as congestion rises.
Vesta also migrates reusable prefixes across length buckets
to avoid cold starts. On real-world agentic workloads, Vesta
improves throughput by 14.0% and reduces mean TTFT by
57.8% over the state-of-the-art scheduler in a PD-colocated
deployment. In PD-disaggregated deployments, it reduces
mean TTFT by up to 18.1% and P99 TTFT by up to 29.0% at
matched throughput.
1 Introduction
Large language models (LLMs) increasingly serve as the
reasoning engine of autonomous agents [2, 20, 21, 27]. Rather
than issuing isolated prompts, an agent solves a task through
a session: it asks the model for a next step, invokes tools,
appends their outputs to the context, and issues the next
request. Consequently, later turns usually extend the context
of earlier ones. Prefix caching can reuse the KV cache of the

shared prefix and avoid most prefill work, making it essential
to efficient agentic serving [6, 7, 37].
Our production trace shown in Section 3.1 confirms that
this reuse is both prevalent and persistent: 80.6% of requests
reuse at least 90% of their prompt. At the same time, the num-
ber of active sessions changes substantially over the course
of a day, so a serving cluster alternates between periods
with abundant idle capacity and periods close to saturation.
These two properties make request placement stateful. The
instance selected for a session determines where its accu-
mulated KV cache can be reused on later turns, while the
instantaneous system state determines whether that instance
can serve the next turn promptly.
Together, these two properties put cache affinity and load
in conflict. Routing a session to the instance that holds its
KV cache minimizes computation, but many active turns
can accumulate at the same cache-affine instance. Other in-
stances may then be idle while requests wait, wasting cluster
capacity. Routing to a less loaded instance instead pools that
capacity, and a hierarchical KV cache can preserve reuse
by fetching the prefix remotely. However, remote execution
incurs KV cache transfer work. It can reduce a request’s im-
mediate wait while increasing the cluster’s service demand
and thus delaying later requests. The appropriate decision
therefore depends not only on cache locality and the holder’s
queue, but also on the cluster’s congestion state.
Queueing theory makes this trade-off explicit. A cache-
affine instance is a queue whose utilization is determined
by the work routed to it. Waiting time grows sharply near
saturation, so moving work away from a locally busy holder
can have a large benefit when other instances have slack. In
contrast, when all instances are busy, the capacity-pooling
opportunity largely vanishes and extra KV cache transfer
work only pushes the cluster closer to saturation. Thus, the
same execution migration should be aggressive under local
congestion in an otherwise underloaded cluster, but con-
servative under global congestion. The system objective is

consequently not only to minimize the latency of a single
request, but also to maximize the throughput the cluster can
sustain.
Recent LLM scheduling systems explore different points
in this design space. LMetric [36] combines cache-locality
and load indicators into a hyperparameter-free scheduling
score. SMetric [29] adopts a session-centric policy that load-
balances the first turn of each session while favoring cache
affinity for later turns unless the assigned instance becomes
overloaded. DualMap [35] routes each request to two can-
didate instances and selects between them according to the
current system state. Another line of work leverages analyti-
cal performance models to estimate candidate-instance be-
havior and guide placement [3, 19, 23, 40]. These approaches
make decisions based on the current system state, taking into
account cache locality, instance load, and predicted latency.
However, they do not explicitly account for the downstream
effects of these decisions. Each decision has two such effects:
first, the KV cache replicas it creates reduce the cluster’s
effective cache capacity, thereby lowering the overall hit ra-
tio and degrading serving performance; second, the placed
request delays subsequently arriving requests.
To account for both effects, we present Vesta, a queueing-
aware scheduler for distributed agentic LLM serving. Vesta
separates two placement decisions that operate at different
timescales. It assigns every session a stable holder, chosen
by hashing the session within its current length bucket, that
retains the session’s authoritative KV cache and thereby
keeps long-term cache ownership balanced across the clus-
ter. For each request, it independently selects an executor. If
the executor differs from the holder, it fetches the reusable
prefix from the holder, executes the request, and writes the
newly generated KV cache back to the holder. This holder–
executor disaggregation addresses the cache-capacity effect:
Vesta can use spare capacity without scattering a session’s
KV cache over the local caches of many instances. Vesta fur-
ther targets bucket-based deployments, in which instances
are grouped into size-homogeneous length buckets so that
batches contain requests of comparable length [38]. Since
agentic sessions grow monotonically across turns, a session
eventually outgrows its bucket and is rehashed to a holder in
a larger one. Vesta then transfers the longest reusable prefix
to that new holder, avoiding a cache cold start at the bucket
boundary.
Vesta then addresses the delay effect when selecting an
executor, by pricing the queueing externality [8] of a place-
ment, i.e., the additional delay it imposes on later requests.
For every candidate, it estimates the unfinished backlog, the
prefill work remaining after local or remote KV cache reuse,
and the KV cache transfer cost. Taking the demand of the
cheapest candidate as a baseline, it charges only the service
demand that a placement adds on top of that baseline, us-
ing a bounded function of cluster utilization and the M/M/𝑐
waiting probability. The price is small when the cluster has

idle capacity, enabling execution migration to relieve a busy
holder; it rises with congestion, favoring placements that
avoid additional transfer and prefill work.
We implement Vesta on vLLM [28] and Dynamo [19], and
evaluate it with real-world agentic traces. On a 32-instance
prefill/decode (PD)-colocated deployment, Vesta improves
throughput by 14.0% over the state-of-the-art scheduler while
reducing mean TTFT by 57.8%. On PD-disaggregated deploy-
ments for Qwen [32] and Hy3 [26], it reduces mean TTFT
by 18.1% and 14.5%, respectively, while retaining comparable
KV cache reuse and throughput. Vesta also lowers tail TTFT,
improves prefill load balance, and reduces P95 and P99 TTFT
by 35.6% and 32.6% when migrating a reusable prefix across
length buckets.
In summary, this paper makes the following contributions:
•We characterize real-world agentic workloads, includ-
ing their KV cache reuse patterns and time-varying
request arrivals.
•We adopt holder–executor disaggregation, which pre-
serves stable session KV cache ownership while allow-
ing each request to execute on a different, less loaded
instance to enable a flexible scheduling strategy.
•We design Vesta with a queueing-aware objective that
balances backlog reduction against the queueing ex-
ternality on later requests, and with cross-bucket KV
cache migration that preserves cache reuse as sessions
lengthen in the bucket-based deployment.
•We evaluate Vesta on production agentic traces in both
serving architectures, demonstrating lower mean and
tail TTFT with higher or comparable throughput.

2.2 LLM Serving Systems
At scale, an LLM service comprises a front-end scheduler and
a collection of GPU instances, each of which hosts a model
replica. The scheduler routes every arriving request to one of
these instances for execution. Serving systems organize the
two inference phases in one of two ways, as shown in Fig-
ure 1. PD-colocated serving assigns both prefill and decode
to the same serving instance throughout a request’s execu-
tion. Consequently, the request’s KV cache remains local
to that instance, avoiding inter-instance KV-cache transfers.
However, the compute-intensive prefill phase and latency-
sensitive decoding share the instance’s GPU resources, which
can lead to resource contention. PD-disaggregated serving
assigns prefill and decode to distinct instance pools [22, 39].
After prefill finishes, its KV cache is transferred to a decode
instance via RDMA, so the two pools can be independently
sized and tuned. Regardless of the serving architecture, reuse
on a subsequent request requires that its KV cache remain
local or be fetched from a remote cache tier.
Within each instance, requests are usually executed under
the optimization technique called continuous batching [34]:
instead of running a fixed batch to completion, the engine
dynamically incorporates newly arrived requests without
waiting for the batch to drain. Compared with static batching,
where a batch slot stays occupied until the longest sequence
in the batch terminates, this greatly improves GPU utilization
under variable prompt and output lengths. Continuous batch-
ing, however, batches requests as they arrive and leaves them

Under such mixed batches, padding to the longest sequence

yields more efficient GPU memory usage. In such a bucket-
based deployment, each bucket is served by its own pool of
instances. Bucketing is thus complementary to cluster-level
scheduling: it determines how requests of similar length are
batched, whereas a scheduler still decides which instance
within a bucket serves each request.
Sustaining cross-request reuse requires retaining the KV
cache of finished requests, but GPU memory alone is far
from sufficient: a single 64K-token request already consumes
10GB of KV cache on the Hy3 model [26]. Production sys-
tems therefore organize the KV cache into a memory hier-
archy [4, 23]. The L1 cache consists of an instance’s device
(GPU) memory, offering faster access but lower capacity. The
L2 cache consists of host (CPU) memory across the cluster,
offering slower access but greater capacity. As illustrated in
Figure 2, an instance can load a reusable prefix from its own
host memory over PCIe, or fetch it from the host memory
of remote nodes over RDMA. Cache blocks are therefore
effectively shared cluster-wide instead of being confined to
the instance that produced them. Consequently, load balanc-
ing need not come at the expense of cache reuse: a request
routed to a less-loaded instance can still reuse its prefix from
the remote L2 cache, incurring a transfer cost rather than
a recomputation cost. In this paper, we build our system
design on this two-tier memory hierarchy, where a GPU can
read the KV cache from both local and remote host memory.

2.3 Agentic Workloads
Requests in agentic workloads are organized into sessions. A
session 𝑠 is the sequence of requests 𝑟1,...,𝑟𝑛 that an agent
application submits to the serving system while working on
a single task, and its state is entirely captured by a context
that the agent maintains on the client side. The context starts
as a system prompt plus the user’s initial task description.
Thereafter, the agent extends it in place: after receiving reply
𝑦𝑖 to request 𝑟𝑖 , it executes the actions requested therein,
typically tool calls, and appends both 𝑦𝑖 and the resulting
tool outputs 𝑜𝑖 to the context before issuing 𝑟𝑖+1. The user
may also intervene between turns, for instance to refine
the task or to approve an action, in which case the new
instruction 𝑢𝑖 is appended as well. The typical context of
successive requests therefore satisfies
ctx(𝑟𝑖+1)= ctx(𝑟𝑖 )⊕𝑦𝑖 ⊕𝑜𝑖 ⊕𝑢𝑖 , (2)
where ⊕denotes concatenation. Two consequences follow:
First, the model is stateless across requests, so the growing
context must be resent in full on every turn, and prompt
length increases monotonically within a session. Second,
and more importantly for the serving system, ctx(𝑟𝑖 )is by
construction a prefix of ctx(𝑟𝑖+1), regardless of whether the
turn was driven by a tool or by the user. Prefix reuse in
agentic serving is thus not an empirical regularity that a
workload happens to exhibit, but a structural invariant of
the interaction with the model.
The arrival process of such real-world workloads is highly
non-stationary: the number of concurrently active sessions
can vary substantially over the course of a day, often reflect-
ing the working hours of the users who drive the agents. As
a result, a serving cluster operates across a broad spectrum
of load conditions: during off-peak periods, much of its ca-
pacity may remain idle, whereas during peak periods, most
instances can become saturated. Since deployments must
be provisioned for peak demand, the primary constraint un-
der these conditions shifts from the latency of individual
requests to the aggregate request rate that the cluster can
sustain.

2.4 A Queueing-Theoretic View of LLM Scheduling
The components of a serving system map naturally onto a
queueing model [8, 9]. The requests arriving at the cluster

much of each request’s prefill can be skipped through KV

the routing policy that decides which queue a request joins on
arrival. Consider first a single instance in isolation. Writing

3 Motivations
3.1 Workload Characterization
We analyze traces collected from real-world agentic work-
loads to characterize their key properties.
High KV Cache Reuse. As shown in Figure 3, 80.6% of
requests reuse at least 90% of their prompt, while 8.3% have
a hit rate below 5%. Thus, the payoff from cache locality
is close to all-or-nothing rather than a quantity that varies
smoothly with placement: a scheduler commonly faces either
a nearly complete KV cache reuse opportunity or none at all.
Preserving cache affinity is therefore particularly valuable for
the former group, whose prefill work can be almost entirely
avoided, while the latter group provides substantially more
placement flexibility.

3.2 Queueing Effects of Cache-Aware Scheduling
To quantify how cache-aware routing affects queueing, we
replay two one-hour traces—Trace 1 with 2,779 requests
and Trace 2 with 4,036 requests—on Qwen2.5-7B-Instruct-
1M [32], based on their original request timestamps. The two
traces represent different load regimes, allowing us to exam-
ine queueing effects under different levels of load pressure.
The serving cluster comprises four prefill and four decode
instances (4P4D), each equipped with one H20 GPU and
128 GB of host DRAM. We compare two scheduling policies.
Cache Affinity pins all requests in a session to the instance
that serves its first request, maximizing local KV cache reuse.
SMetric [29] is a session-centric policy that load-balances a
session’s first request and routes follow-up requests to the
same instance for cache affinity; it migrates a session’s pre-
fill to another instance only after its cache-affine instance
becomes overloaded.
Figure 6 decomposes TTFT under the two policies into
queueing and computation time. At the lower average clus-
ter utilization of 29% in Trace 1, SMetric reduces average
TTFT from 2,819.14 to 2,059.86 ms (26.9%). More importantly,
queueing falls from 699.76 ms (24.8% of TTFT) under Cache
Affinity to 261.52 ms (12.7%) under SMetric. At the higher
45% utilization of Trace 2, this gap widens: SMetric reduces
TTFT from 5,456.99 to 3,328.95 ms (39.0%) and queueing from
2,697.80 ms (49.4% of TTFT) to 1,038.00 ms (31.2%). Hence, as
utilization rises, queueing becomes the dominant source of
Cache Affinity’s TTFT inflation. Although SMetric alleviates
this effect, its reactive, overload-triggered migration leaves
substantial queueing delay, particularly in Trace 2.

4 Vesta: Queueing-Aware Scheduling
4.1 Holder-Executor Disaggregation
Before presenting the scheduling algorithm, we describe
Vesta’s serving architecture. Our workload characterization
exposes a fundamental tension between cache affinity and
load balance. Strong intra-session KV cache reuse eliminates
most prefill computation for follow-up requests, reducing
server utilization and increasing the effective service rate.
Cache-affine routing exploits this benefit by directing a ses-
sion’s requests to the instance that holds its KV cache. How-
ever, it can create severe local queueing when that instance is
busy, even if other instances have spare capacity. The global
L2 cache hierarchy provides a way to resolve this tension:
another instance can fetch and reuse the prefix remotely,
paying a transfer cost rather than recomputing it.
Vesta exploits this capability by decoupling KV cache own-
ership from request execution. As shown in Figure 7, each
session 𝑠 is associated with a holder ℎ(𝑠), whose role is to
maintain the authoritative KV cache of 𝑠 across turns. For
each request, Vesta selects an executor 𝑒from the serving in-
stances to perform the computation. The executor can be the
holder itself: when 𝑒 = ℎ(𝑠)(Figure 7a), it reads the reusable
KV cache locally and executes without a network transfer.
Alternatively, when the holder is busy and another instance
offers lower queueing pressure, Vesta can choose 𝑒 ≠ ℎ(𝑠)
(Figure 7b). The remote executor fetches the reusable prefix
from the holder’s L2 cache into its HBM, performs the pre-
fill computation, and writes the newly generated suffix KV
cache back to the holder.
Notably, the remote executor does not offload either the
fetched prefix KV cache or the newly generated suffix KV
cache to its local L2 cache. Such replicas would occupy L2
cache that could instead hold the KV cache of the sessions
this instance holds, thereby reducing the cluster’s effective
cache capacity. Instead, these KV caches remain in HBM and
can be reused if a subsequent request from the same session
is again assigned to this executor. The executor then fetches
only the newly missing suffix from the holder, substantially
reducing the remote-transfer cost of subsequent execution
migration when the holder is busy and this remote executor
remains lightly loaded. Because L2 cache capacity is much
larger than HBM capacity, retaining execution-side copies
in HBM does not reduce the L2 capacity available for the
instance to serve as a holder for other sessions.
This write-back protocol preserves the holder as the owner
of the longest KV cache accumulated for its session despite
dynamic execution placement. Subsequent turns can there-
fore always locate the session’s complete KV cache at ℎ(𝑠),
while Vesta remains free to migrate the current turn to a
less-loaded executor. Holder-executor disaggregation thus
retains the long-term cache locality required by agentic ses-
sions while recovering the short-term capacity-pooling op-
portunity needed to reduce queueing. The scheduler must

4.3 Queueing-Aware Executor Selection
After fixing a session’s holder, Vesta selects an executor for
each request by jointly considering its predicted completion
time and the additional service demand introduced by its
placement. This distinction is essential. Routing a request
away from a busy holder can reduce its immediate queueing
delay, but it may also require extra KV-cache movement and
prefill work. The latter increases cluster utilization and, as
Equations (4) and (8) show, can sharply increase queueing
delay as the system approaches saturation.
For a request with 𝑁 prompt tokens, let 𝐺𝑖 denote the
longest reusable prefix already resident in candidate execu-

available anywhere in the cluster’s L2 cache, located through
the KV cache indexer. Once the holder has served a turn
of the session, the write-back protocol makes its copy the
longest, so 𝐻 resides at ℎ(𝑠). Two cases depart from this. On
a session’s first turn the holder has cached nothing for it, so

5 Evaluation
5.1 Experimental Setup
Implementation. Our cluster comprises 12 GPU servers
totally, each equipped with 8 NVIDIA H20 GPUs (96 GB
HBM each), 96 CPU cores, and 1,024 GB of DRAM. The
servers are interconnected via 200 Gb/s RDMA NICs. The in-
stances in the cluster are running the same vLLM engine [28].
Dynamo [19] serves as the KV cache indexer, tracking the
locations of KV cache blocks across instances to support
cache lookup and prefill latency estimation. Empirically, we
set the congestion-price exponent 𝛾= 0.5 and cap 𝜋max = 2
for Vesta in all experiments.
Models. We evaluate Qwen2.5-7B-Instruct-1M [32] and Hy3-
FP8 [26], two models at different scales that both support
long contexts. Each Qwen2.5-7B-Instruct-1M instance uses
one GPU, whereas each Hy3-FP8 instance uses eight GPUs.
Real-World Agentic Workloads. We collect Trace Agent,
a one-hour trace of peak-time real-world agentic workloads
(36K requests in total, mean input length: 83K, P90 input
length: 133K), from an online serving system. In all exper-
iments, we replay the trace according to its original times-
tamps to preserve the observed request-arrival pattern, while
serializing requests within each session to prevent concur-
rent processing of dependent turns. Following prior work [29,
36], we force each evaluated model to generate exactly the
number of tokens recorded in the trace.
Baselines. We compare Vesta with the state-of-the-art LLM
scheduling strategies including LMetric [36] and SMetric [29].
LMetric uses the product of the number of uncached to-
kens and batch size as its scheduling score. SMetric adopts a
session-centric policy that load-balances first-turn requests
and routes follow-up requests to the same instance for cache
affinity, unless that instance is overloaded or the session’s
KV cache has been evicted.

Architecture
We evaluate Qwen2.5-7B-Instruct-1M with 32 instances on
Trace Agent, each colocating prefill and decode execution.
Figure 8 compares the serving performance of LMetric,
SMetric, and Vesta in the PD-colocated setting. Vesta achieves
both the highest tokens per second (TPS) and the lowest
mean TTFT. Figure 8b shows that Vesta reaches 53.4 tokens/s,
13.9% higher than SMetric (46.9 tokens/s), the stronger base-
line for TPS, and 39.8% higher than LMetric (38.2 tokens/s).
This improvement does not come at the cost of a longer
wait for the first token: Figure 8a shows that Vesta reduces
mean TTFT to 1,685.63 ms, compared with 3,993.89 ms under
SMetric (57.8% lower) and 5,568.87 ms under LMetric (69.7%
lower).
Figure 8a also reports the queueing delay, which accounts
for much of this TTFT gap. Although SMetric has lower
mean TTFT than LMetric, its mean queueing delay is higher:
1,463.64 versus 296.04 ms. Vesta lowers this delay to 63.91 ms,
a reduction of 95.6% relative to SMetric and 78.4% relative
to LMetric. Consequently, the fraction of mean TTFT spent
waiting falls from 36.6% under SMetric to 3.8% under Vesta. It
is consistent with Vesta’s queueing-aware executor selection:
rather than preserving affinity until an overload condition
triggers migration, Vesta weighs each candidate’s backlog
against its service cost for every request. Its congestion-
priced objective in Equation (15) is designed to exploit capac-
ity beyond a busy holder while accounting for the additional
service demand of migration.
The latency percentiles further distinguish the schedulers.
Figure 8c shows that Vesta has the lowest TTFT at every re-
ported percentile. Relative to SMetric, Vesta reduces P90
and P95 TTFT by 68.5% and 58.9%, respectively. At P99,
LMetric is the stronger baseline, despite its higher mean
TTFT: it reaches 32,713.80 ms versus 40,366.72 ms under
SMetric. Vesta lowers P99 TTFT to 20,457.44 ms, 37.5% be-
low LMetric and 49.3% below SMetric. Figure 8d shows zero
queueing delay for Vesta at all four reported percentiles,
whereas P99 queueing reaches 8,065.00 ms under LMetric
and 28,143.52 ms under SMetric. These zero percentiles do
not imply that every request avoids queueing, as Vesta’s
mean queueing delay remains nonzero. Together, the results
show that Vesta improves TPS while reducing both mean
TTFT and the measured latency tail in this PD-colocated
experiment.
Despite its higher TPS and lower mean TTFT, SMetric
has 23.4% higher P99 TTFT and 3.49×the P99 queueing de-
lay of LMetric. This reversal highlights that improvements
in throughput and mean latency do not necessarily trans-
late into better tail performance. This observation aligns
with Vesta’s motivation to jointly model KV cache transfer
costs and their queueing externality: the additional service
demand induced by migration can amplify waiting near sat-
uration, even when migration benefits the current request.

TPS. Figure 14 shows that Vesta retains essentially the same

6 Related Work
6.1 LLM Scheduling
At the cluster level, online schedulers adapt request place-
ment to changing load. Llumnix performs cross-instance
rescheduling through live migration of in-memory request
state, whereas AdaGen adapts cluster routing and compute
layouts to workload changes [24, 25]. Recent work combines
cache-locality and load signals in request placement [35,
36], and SMetric adopts a session-centric policy that load-
balances the first request of a session before favoring cache
affinity for its follow-up requests [29]. Analytical schedulers
further estimate candidate-instance latency or SLO compli-
ance to guide placement [3, 23, 40]. Vesta likewise reconciles
cache reuse with load balance, but from a queueing-theoretic
perspective: it decouples stable session cache ownership
from per-request execution and weighs the queueing benefit
of migration against its cache-transfer cost under the current
cluster load.
6.2 LLM Inference Optimization
Token and KV Cache Compression. Long contexts make
attention and KV cache storage the dominant costs of infer-
ence. Sparse-attention and token-selection methods select
a small set of context tokens for each query, reducing the
attention work during prefill and decode [11, 14, 15, 30]. KV
cache quantization instead stores keys and values at lower
precision, reducing the memory footprint and allowing a
fixed-capacity cache tier to retain more prefixes [10, 17].
Model Architecture. Architectural co-design changes the
representation or computation performed by the model itself.

Linear-attention architectures replace the quadratic softmax-
attention operation with a recurrent or kernelized formula-
tion whose cost scales linearly with context length [5, 12, 33].
Grouped-query attention reduces the number of distinct
KV heads during decoding [1], while recent long-context
models combine multi-head latent attention with sparse-
attention mechanisms to reduce KV cache size and attention
cost [16, 31]. These techniques improve the execution effi-
ciency of an individual request and are complementary to
Vesta, which instead operates at the cluster level.
7 Conclusion
We presented Vesta, a scheduler that grounds agentic LLM
serving in queueing theory. Vesta maintains a stable holder
for each session’s KV cache while selecting an executor per
request, using spare capacity without scattering that cache.
Its objective prices the queueing externality of a placement,
migrating execution under slack and favoring the least ad-
ditional transfer and prefill work as congestion rises. Vesta
also migrates reusable prefixes across length buckets to avoid
cold starts as sessions lengthen. On production agentic traces,
Vesta reduces mean and tail TTFT in both serving architec-
tures while achieving higher or comparable throughput.
